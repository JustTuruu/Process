# Lab 1 — UI автомат тест — Playwright

F.CSA313 — Программ хангамжийн чанарын баталгаа ба тест (2026)

## Юу хийсэн бэ

Энэ төсөл нь [saucedemo.com](https://www.saucedemo.com) демо дэлгүүр дээр Playwright ашиглан
3 UI автомат тест бичсэн:

- **амжилттай нэвтрэх** (`standard_user` / `secret_sauce`) — Products хуудас руу шилжиж буйг шалгана
- **амжилтгүй нэвтрэх** — буруу нууц үгээр нэвтрэхэд алдааны мессеж гарч буйг шалгана
- **нэвтэрсний дараах үйлдэл** — бараа сагслаад, сагсны тоо зөв өөрчлөгдсөнийг шалгана

Тестүүд `tests/saucedemo.spec.ts` файлд байрлана. Element олоход `getByRole`, `getByPlaceholder`,
`getByText` зэрэг орчин үеийн locator-ууд ашигласан бөгөөд XPath огт ашиглаагүй (доор шалтгааныг
тайлбарласан). Тест бүр logout-оор төгсдөг тул бие биенээсээ хамааралгүй, дангаараа ажиллана
(test isolation).

## Ажиллуулах заавар

```bash
npm install
npx playwright install
npx playwright test
```

Зөвхөн саучедемогийн тестийг харах бол:

```bash
npx playwright test tests/saucedemo.spec.ts --reporter=list
```

HTML report үзэх:

```bash
npx playwright show-report
```

## Trace бичлэгүүд

`test-artifacts/` фолдерт хадгалагдсан 2 trace жишээ бий:

- `passing-trace-demo.zip` — бүх assertion зөв, тест амжилттай давсан үеийн trace
- `failing-trace-demo.zip` — сагсны тоог санаатайгаар буруу утгаар (`toHaveText("2")`) шалгуулж,
  тестийг санаатай унагаасны дараах trace. алдаа хэрхэн гарч, DOM snapshot дээр юу болсныг
  trace viewer-ээр алхам алхмаар харж болно

Trace viewer дээр нээх

```bash
npx playwright show-trace test-artifacts/failing-trace-demo.zip
```

## XPath-аас яагаад ашиглаагүй шалтгаан

`getByRole`/`getByPlaceholder`/`getByText` зэрэг нь хэрэглэгчийн бодитоор харж, харилцаж буй
зүйл дээр (buttonii нэр, талбар placeholder, дэлгэц дээрх текст) тулгуурладаг тул хуудасны дотоод
HTML бүтэц (div-ийн бүрхэвч, class нэр) өөрчлөгдсөн ч тест эвдрэхгүй байх магадлал өндөр байдаг.
Харин XPath нь ихэвчлэн DOM-ийн бүтцэд (`div[3]/span[2]` гэх мэт) шууд тулгуурладаг тул хуудасны
верстка бага зэрэг өөрчлөгдөхөд ч амархан эвдэрдэг. засварлахад хугацаа их зарцуулдаг, тогтвортой
бус тест үүсгэдэг гол шалтгаан нь энэ юм.

## Codegen туршилт

```bash
npx playwright codegen saucedemo.com
```

командаар үйлдлээ бичүүлж, гарсан кодыг гараар бичсэн тесттэйгээ харьцуулав. Codegen нь click,
fill зэрэг үйлдлийг маш хурдан бичиж өгдөг боловч ихэвчлэн CSS selector (жишээ нь `#login-button`)
дээр тулгуурлан код үүсгэдэг тул үүнийг гараар `getByRole`/`getByPlaceholder` гэх мэт илүү тогтвортой
locator болгон засварлах шаардлагатай болдог. Мөн assertion (`expect`) codegen автоматаар нэмдэггүй —
энэ хэсгийг үргэлж гараар нэмж бичих ёстой.

## Playwright vs Selenium — ажиглалт

Энэ лабораторийн явцад Playwright ашиглаж үзсэний дараа Selenium-тэй харьцуулахад дараах ялгаануудыг мэдсэн.
Playwright-ийн auto-wait механизм нь элемент бэлэн болтол автоматаар хүлээдэг тул
Selenium дээр байнга бичдэг явцын `WebDriverWait`, `time.sleep` гэх мэт нэмэлт код бичих шаардлагагүй
болсон нь тестийн кодыг илт цэвэрхэн, богино болгож байна. Мөн Playwright нэг л командаар (`npx
playwright install`) chromium, firefox, webkit гурван хөтчийг нэгэн зэрэг суулгаж, нэг тестийг гурван
хөтчөөр зэрэг ажиллуулах боломжтой байсан нь Selenium дээр хөтөч бүрд тусдаа driver татаж тохируулах
процесстой харьцуулахад хамаагүй хялбар санагдлаа. Хамгийн их таалагдсан зүйл бол trace viewer
байсан бөгөөд тест унасан үед алхам бүрийн screenshot, DOM snapshot, сүлжээний хүсэлтийг цаг хугацаагаар
нь буцааж харах боломж нь Selenium-ийн энгийн лог/скриншотоос хамаагүй дэлгэрэнгүй бөгөөд алдаа
олоход хэрэглэгчид цаг хугацаа хэмнэж байгааг мэдэрлээ. Codegen функц нь эхлэн суралцагчид маш
хэрэгтэй — гараар locator бичихээс өмнө хуудасны бүтцийг ойлгоход тусалдаг. Гэхдээ Selenium илүү
удаан хугацаанд хэрэглэгдэж ирсэн тул баримтжуулалт, community жишээ илүү олон, мөн зарим хуучин
корпорацийн систем эсвэл байгууллагад Selenium-ийн дэд бүтэц аль хэдийн бий болсон тохиолдолд шинээр
Playwright руу шилжих нь нэмэлт зардал шаардаж болзошгүй юм. Хэлний дэмжлэгийн хувьд хоёул JS/TS,
Python, Java, C#-ийг дэмждэг тул энэ талаараа онцын ялгаа мэдрэгдсэнгүй. Нийтдээ, шинэ төсөл эхлүүлж
байгаа бол Playwright-ийн хурд, тогтвортой байдал, дебаг хийхэд хялбар байдал нь илүү давуу тал
болохыг энэ лабораторийн ажлаар мэдэрлээ.

## AI ашигласан тухай

Лабораторийн даалгаврыг гүйцэтгэхдээ эхлээд өгөгдсөн шаардлагуудыг өөрөө ойлгож, Playwright ашиглан шаардлагатай UI тестүүдийг гараар бичсэн. Үүний дараа бичсэн тестүүдээ ажиллуулж, бүх тест зөв ажиллаж байгаа эсэхийг шалгасан. Дараагийн алхамд ижил шаардлагуудыг AI-д өгч, Playwright ашиглан тестүүдийг хэрхэн шийдэхийг санал болгуулсан. AI-ийн үүсгэсэн кодыг өөрийн бичсэн кодтой харьцуулж, locator сонголт, тестийн бүтэц болон assertion-уудын ялгааг шалгасан. Харьцуулалтын явцад AI-ийн санал болгосон хувилбар нь `getByRole`, `getByPlaceholder` зэрэг Playwright-ийн хэрэглэгчийн үйлдэлд суурилсан locator-уудыг ашигласан бөгөөд тестийн үндсэн логик нь миний гараар бичсэн хувилбартай ерөнхийдөө ижил байсан. Гэхдээ AI-ийн үүсгэсэн кодыг шууд ашиглахаас илүүтэйгээр тухайн кодын зөв эсэхийг өөрөө шалгаж, шаардлагатай хэсгүүдийг өөрийн ойлголт болон лабораторийн шаардлагатай харьцуулан үнэлсэн. Ингэснээр AI нь тестийн кодыг хурдан үүсгэхэд тусалж болох боловч үүсгэсэн кодын зөв ажиллагаа, locator-ийн тогтвортой байдал, assertion-ийн зөв эсэхийг хөгжүүлэгч өөрөө шалгах шаардлагатай гэдгийг ажигласан.
